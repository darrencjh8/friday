QUESTIONS
q: Is the defect only OCBC wording, or a shared flow? | a: shared. `_resolveMovementToOutput` hardcodes `Misc` for every incoming movement with no counterparty (the `movement.direction === "incoming" && !movement.counterparty` branch of `_resolveMovementToOutput`), the Phase 2 merchant tier is skipped for any prepopulated payee (the `!output.payee_name && searchTerm` guard in `_resolvePhase2`), and `_handle_resolve_merchant` (`tools.js`) returns `Misc` after a memory miss for every caller (outgoing merchants included). The LLM-extractor and ordinary Phase 1 routes reach the same `resolve_merchant` tier, so fixing the resolver once covers them.
q: Where does the exact reference get lost? | a: `extractEmailContent` collapses all whitespace (`extractEmailContent` in `extractors.js`), so `field()` in `bank-movement.js` (`[^\n]+`) reads from `Reference:` to the end of the flattened body. The email's own line breaks are the only reliable field boundary, so the plan keeps a second, line-preserving extraction as evidence and uses it to bound the reference. The existing flattened text still feeds the parser and Phase 1 unchanged.
q: Which Jev request shape? | a: the documented System One shape, the same one the dev-loop driver already uses: `POST https://api.typesafe.ai/v1/systemone` with `Authorization: Bearer $JEV_API_KEY` and `{model: "jev-latest", state, questions}`. A `choice` question answers with `choice`, per-option `probabilities` and `confidence`; a `noul` question answers with a probability under `noul`. Choice takes 1 to 255 options. Answers are read from `answers` when present, else from the top level, because the vendor docs show both.
q: How do "best match, runner-up, confidence, supporting evidence" map onto typed answers? | a: two sequential System One calls over the same `state`, each with a 20 second timeout and no retry. Call 1 is a `choice` over every eligible payee plus one explicit "none of the listed payees" option: best = `choice`, runner-up = the next highest probability, confidence = `confidence`. Call 2 is made only when call 1 passed validation, and is a `noul` about that winning payee ("does the email text itself state or directly imply this payee, beyond general knowledge of the label?"): supporting evidence = that probability. A failure, timeout or malformed answer in either call leaves `Misc`, and call 2 is never sent when call 1 already failed. The matched descriptor is kept as the human-readable evidence in the notification.
q: What is accepted? | a: the choice must be exactly one eligible payee (not the none option), `confidence >= 0.85`, `probabilities[best] - probabilities[runner_up] >= 0.30` (a missing probability map rejects), and the evidence `noul >= 0.80`. Anything else, an HTTP error, a timeout, a malformed answer, a missing `JEV_API_KEY`, or more than 255 eligible payees leaves `Misc`. The thresholds are constants in one place and are covered by boundary tests (just above and just below each). They are initial values to calibrate, not ground truth; a model score alone never books anything the validation rejects.
q: Which payees are eligible? | a: every payee returned by `fetch_context`/`/payees` except account-transfer payees (`transfer_acct` set), `Misc`, `Starting Balance`, blanks, and any name that appears more than once case-insensitively (an ambiguous name fails `AMBIGUOUS_PAYEE` at insert). `OCBC 360` is a transfer payee, so it can never be chosen. `Bank Interest` stays eligible. Jev's answer is re-validated against that list by exact name after the call.
q: Can email content steer the model or the tools? | a: it can bias a classification and nothing else. The call is a typed classifier with no tools; the email sits between markers in the `state` string that declare it untrusted data; a literal closing marker inside the text is neutralised; the returned payee must be an exact eligible name; and no output is ever executed or learned automatically.
q: What is sent to Jev? | a: the line-preserved body text (capped at 6000 characters), the subject, the sender header value, direction and amount, and the descriptor. URLs are replaced by `[link]` (tracking links carry tokens) and digit runs of 8 or more are masked to their last four digits. No raw MIME headers, attachments, credentials or `.env` values are sent. The `evidence` argument is removed from `executeTool`'s `tool_exec` log line, and the new code logs only the payee names, confidences and a reason code, never the email text.
q: How does a deposit with no counterparty reach the resolver without breaking pinned behaviour? | a: the deterministic branch still returns `payee_name: "Misc"`, `_structured_movement: true` and the same amount/account/date, but now sets `merchant`/`raw_description` to the exact reference only when it passes the descriptor check (below), otherwise it keeps `Unidentified deposit`; the reference is written into `notes` either way; and `_payee_unresolved: true` is set. Phase 2 clears the prepopulated `Misc` when that flag is set, so the existing memory, `resolve_merchant` (now carrying the evidence), `Misc` tiers run. Pinned fixtures that keep `Unidentified deposit`: the empty-reference deposits in `bank-movement.test.js` and `production-incidents.test.js`, and the #680 fixture in `incoming-credit-booking-680.test.js` whose only reference is the all-digit `Transaction Ref` (it fails the ID-like check).
q: What counts as a usable descriptor? | a: `descriptorOf(text)` in `learning.js` returns the trimmed text only when it matches `^[A-Za-z0-9][A-Za-z0-9 &'./*#-]{2,39}$`, has at least three letters, has digits making up at most half of its non-space characters (so a transaction id or all-digit reference is rejected), and contains none of the memory grammar tokens `maps to`, `payee`, `category`, `belongs to`, `alert recipient`, `is a`, `is an` (case-insensitive). Anything else is not used as the merchant, is never offered for learning, and still goes to Jev as part of the full evidence. This keeps a stored fact reading back as the payee the user confirmed, because the readers' lazy `maps to (.+?) payee` can only match the one clause the tracker writes.
q: Does this weaken the internal-transfer and person holds? | a: no. The change is confined to the `!counterparty` incoming branch and the payee-tier guard. The person hold, the internal-transfer arm, the #680 named-credit arm, the PayNow identity branch, dedup, linking and account/date ownership are untouched, and Phase 2's transfer detection still runs on whatever payee the resolver returns. Transfer payees are excluded from Jev's options, and a memory-mapped payee keeps today's behaviour.
q: How is learning kept behind real user confirmation? | a: the pipeline never writes a fact for a Jev result. After the insert succeeds, and only when the descriptor passed `descriptorOf`, Phase 3 stores a pending offer (descriptor, payee, runner-up, budget) in a small file-backed store (`data/pending-learning.json`, 7-day expiry, 50-entry cap, random 8-character id, atomic write by temp file and rename). The notification the tracker writes says `Remember "<descriptor>" as <payee>? Nothing is saved until you confirm.` and deliberately carries no id. The id is only obtainable by the read-only `list_pending_learning` tool. Only `confirm_learning({id})` persists the exact `<descriptor> maps to <payee> payee` fact through the existing `learn_fact` path (so the account-identity validation still applies), consuming the offer only when that write succeeded; `decline_learning({id})` discards an offer. Neither touches the booked transaction. `propose_learning` is internal and is not registered on the HTTP routes or the MCP server. If the notification is not delivered the offer is discarded. The Hermes skill is updated to call `list_pending_learning` and then `confirm_learning` only after the user answers an offer in a later turn, and never to `learn_fact` a Jev mapping directly.
q: Is that a hard boundary against a model confirming on its own? | assumption: the tracker cannot prove a human typed "yes", because the tracker has no inbound user channel and every tool is model-callable; the Hermes `notify` route also relays the message through the model with a no-tools instruction. What the tracker enforces itself is: (1) the pipeline never calls any learn path for a Jev result, so nothing is persisted without a `confirm_learning` call (tested); (2) the id that authorises that call is not in the notification or in the logs, so text inside a hostile email cannot carry it and an injection would have to induce two tool calls instead of reproducing a string; (3) the descriptor is restricted by `descriptorOf` so an offer cannot carry sentences or memory grammar, and the offer text is generated by the tracker with the descriptor quoted as data; (4) ids are random, single-use, expire after 7 days, and a wrong or reused id fails closed. The residual is that a compromised Hermes session can still call the two tools, exactly as it can already call `learn_fact` with no code at all, so the new path adds no capability; closing it needs a Hermes-side approval primitive (for example a Slack interactive callback), which is out of scope and will be filed as a follow-up issue.
q: Does existing legitimate user-approved memory still work? | a: yes. `learn_fact`, `update_fact`, `delete_fact` and the suffix-fact flow are unchanged; a user who teaches a mapping directly still uses `learn_fact`. The account-type and suffix facts the pipeline writes today are not Jev guesses and stay automatic.
q: Do callers outside the orchestrator get Jev? | a: no. `resolve_merchant` called without `evidence` behaves exactly as today (memory, then `Misc`). The orchestrator is the only caller that supplies `evidence`: it calls `registry.executeTool` directly, while the generic HTTP tool route removes an `evidence` field from the request body before dispatch and the MCP route's zod shape does not declare it (zod drops unknown keys, tested), so Hermes and any HTTP client cannot spend a Jev call or inject evidence.
q: Where does `JEV_API_KEY` come from, and what if it is absent? | a: `config.js` reads `JEV_API_KEY` (and optional `JEV_ENDPOINT`/`JEV_MODEL`); `docker-compose.yml` passes `JEV_API_KEY=${JEV_API_KEY:-}` to the expense-tracker service as it already does for Hermes. Absent key means the Jev tier is skipped and behaviour equals today's. The key is never logged or committed.
q: Can the full suite run on this host? | assumption: no. Production has no npm and must not run native lifecycle scripts, so dependencies were installed with `--ignore-scripts` into the isolated worktree; `sharp` and `better-sqlite3` never build, and 31 test files (239 tests) fail at base for that reason alone. The new test files mock `@xenova/transformers` and `better-sqlite3` and run offline here; the regression comparison is the set of failing tests at base against HEAD, and CI is the authority for the full suite.
q: Which dev-loop workarounds apply? | a: darrencjh8/codex-router#403 (the repro overlay copies only Python tests): the reproduction command writes the test from a hashed blob. #412 (native OpenCode support) is only filed and is not claimed fixed.

## Intent

An alert that cannot be classified deterministically is booked as `Misc` and loses what the email said. Issue #720 (an OCBC 360 `360 SAVE BONUS` deposit booked as `Unidentified deposit`) is one case of that. This change keeps the email as evidence, lets Jev choose among the user's real payees when memory has no answer, rejects weak answers, and learns a mapping only when the user confirms it.

## Change

1. `src/extractors.js`: `extractEmailContent(raw, password, { keepLines })`. With `keepLines` it collapses horizontal whitespace only and keeps line breaks; the default output is byte-identical to today.

## Risks

- Eligible payees are not direction-aware, so a Jev answer for a credit could name an expense payee; the state frames the credit as money received and the evidence question must also pass. A direction-aware filter needs payee kinds Actual does not expose.
- A confident but wrong Jev payee can still be booked for an outgoing merchant. Mitigations: exact-name validation, the three thresholds, the evidence question, and no learning. The user can correct it and decline the offer.
- `keepLines` for an HTML-only email cannot recover line breaks that cheerio already flattened; the deposit then keeps `Unidentified deposit` as its descriptor and Jev still sees the full text. Accepted; the upgrade is block-aware HTML text.
- Calibrating the thresholds needs real traffic. They are named constants for that reason.
